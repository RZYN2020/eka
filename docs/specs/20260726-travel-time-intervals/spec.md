# 旅行时间区间模型 Spec

## Overview

本功能把旅行数据统一为递归的地点时间模型，由主基地人生阶段、持续驻留地点和短暂访问地点
共同派生人生轨迹。用户播放或拖动时间轴时，路线必须反映当时实际所在的基地层级：普通旅行
返回当前基地，次主基地期间的短程旅行返回次主基地，阶段末尾则从最后一个持续驻留地点直接
进入下一主基地。实现必须删除 `oneWay` 等单条经历特例，并保持现有地图视觉与控制方式。

## User Stories

### Story 1: 人生阶段中的默认所在地

- **Acceptance**: 当一个主基地阶段的某段时间没有持续驻留或短暂访问覆盖时，生成路线以该主基地作为默认所在地，不产生额外虚构地点。
- **Technical implementation**: `src/data/travel.js` 提供连续的主基地阶段；`src/lib/travel-journey.js` 维护当前基地栈并派生路线。

### Story 2: 普通旅行返回当时的基地

- **Acceptance**: 主基地期间的普通旅行返回主基地；次主基地期间的普通旅行返回次主基地。
- **Technical implementation**: 递归地点节点用 `kind: 'visit'` 表达点状访问；路线生成器从基地栈顶部生成出发与返回节点。

### Story 3: 持续驻留与阶段末尾承接

- **Acceptance**: 持续驻留早于父阶段结束时返回父基地；最后一个持续驻留与父阶段同时结束时，不生成返回父基地节点，而是从持续驻留地点进入下一主基地。
- **Technical implementation**: 递归地点节点用 `kind: 'stay'` 表达持续驻留；路线生成器比较子节点与父容器的机器可读 `end`。

### Story 4: 保留模糊日期的真实顺序

- **Acceptance**: 只知道月份或季节的地点不获得虚构的具体日期；同一机器时间的多个地点按 `sequence` 稳定排序，模糊结束边界按 `endSequence` 定位，页面继续显示原始 `label`。
- **Technical implementation**: `src/lib/travel-time.js` 校验部分 ISO 日期并提供稳定比较；显示文本与排序字段分离。

### Story 5: 错误数据在构建前被发现

- **Acceptance**: 子地点越出父容器、结束早于开始、持续基地重叠、缺少结束时间或主基地阶段不连续时，数据验证必须失败并指出相关城市。
- **Technical implementation**: 时间模型验证集中在旅行时间库，并由数据测试及地图初始化共同调用。

### Story 6: 现有地图交互保持稳定

- **Acceptance**: 自动播放、暂停、下一步、点击刻度、拖动时间轴和键盘定位继续工作；派生回程节点不显示为用户可选的真实事件刻度。
- **Technical implementation**: `src/scripts/travel-map.js` 继续消费派生的 `JourneyStop`，浏览器测试验证关键事件与控制状态，不只依赖固定节点总数。

### Story 7: 显式连续行程

- **Acceptance**: 同一段多城市旅行中的地点依次连接，只在整段行程结束后返回当时的基地；没有显式分组的普通访问仍逐次返回基地。
- **Technical implementation**: 相邻 `visit` 通过相同的 `journeyId` 声明属于同一连续行程，路线生成器按组派生一次出发和一次最终回程。

### Story 8: 键盘与稳定缩放

- **Acceptance**: 用户可以通过键盘启动、暂停、步进和退出人生轨迹；时间轴、地点条目及 Leaflet 地图保留各自的标准键盘操作。悬停地点后再缩放或平移地图时，Marker 必须保持与地理坐标对齐。
- **Technical implementation**: 全局快捷键只在非交互元素聚焦时接管；Marker 强调动画只作用于图标内层，不得覆盖 Leaflet 外层定位 transform。

### Story 9: 已确认的跨城市连续路线

- **Acceptance**: 用户明确提供途经顺序的旅行必须逐站连接，只在明确返回当时基地或进入下一主基地时结束，不得在中途自动插入基地。
- **Technical implementation**: 每段独立旅行使用稳定且互不混淆的 `journeyId`；显式经过同一城市两次时保留两个真实访问节点。

## Functional Requirements

| ID | Requirement | Acceptance check |
| --- | --- | --- |
| FR-1 | 系统必须使用统一的递归地点节点表达主基地阶段、持续驻留和短暂访问；节点类型分别为 `phase`、`stay`、`visit`。 | 数据测试断言三种节点都能被校验与派生；生产数据不再包含 `baseLike` 或 `oneWay`。 |
| FR-2 | 每个已结束地点必须具有机器可读的 `date.start` 与 `date.end`；支持部分 ISO 日期和 `YYYY-spring/summer/autumn/winter` 季节值，当前持续的最后一个主基地允许 `date.end: null`。 | `node scripts/verify-travel-time.mjs` 覆盖合法、缺失、季节值及非法边界。 |
| FR-3 | `visit` 在未知持续时间时必须令 `end = start`，并作为点状事件处理；系统不得据此伪造具体日或月份。 | 测试验证月份级和季节级访问保留机器值及原始 `label`。 |
| FR-4 | `phase` 与 `stay` 必须使用半开区间 `[start, end)`；子节点必须完整包含在父容器区间内，点状 `visit` 必须满足 `parent.start <= visit.start < parent.end`。日期精度相同时使用 `sequence/endSequence` 比较边界。 | 数据验证测试覆盖边界内、越界及同月位于结束边界前后的访问。 |
| FR-5 | 非当前主基地必须首尾连续，即前一 `phase.end` 等于后一 `phase.start`；最后一个当前主基地必须是唯一允许 `end: null` 的顶层节点。 | 生产数据测试断言全部主基地连续且仅最后一个为进行中。 |
| FR-6 | 当没有子事件发生时，当前实际所在地必须是基地栈顶部；初始基地栈只包含当前主基地。 | 合成数据测试验证主基地阶段的事件间隙不会生成其他地点。 |
| FR-7 | 进入 `stay` 时系统必须将其压入基地栈；其内部 `visit` 结束后必须返回该 `stay`，不得返回外层主基地。 | 杭州场景中的普通访问必须形成 `杭州 → 嘉兴 → 杭州` 和 `杭州 → 南京（夏令营）→ 杭州`。 |
| FR-8 | 普通 `visit` 必须从基地栈顶部出发，并在同一机器时间派生返回基地节点；连续两个普通访问之间必须经过当前基地。 | 合成测试验证 `基地 → 访问 A → 基地 → 访问 B → 基地`。 |
| FR-9 | `stay.end` 早于父容器 `end` 时，系统必须派生返回父基地节点。 | 深圳等次主基地场景验证结束后返回南京。 |
| FR-10 | 最后一个 `stay.end` 等于父容器 `end` 时，系统不得派生返回父基地节点；下一主基地必须从该 `stay` 直接承接。 | 2020 年路线片段必须为 `兰州 → 庆阳 → 南京`，且不得在庆阳和南京之间出现兰州。 |
| FR-11 | 点状 `visit` 即使是父容器最后一个事件，也不得承担阶段承接；只有 `stay` 可以成为阶段末尾的实际所在地。 | 合成测试验证父阶段末尾的普通访问仍返回当前基地。 |
| FR-12 | 日期必须先归一化为可比较时间，再按数值 `sequence` 排序；模糊的结束边界可用 `endSequence` 表示同一精度内的离开顺序；相同时间和相同顺序时保持源数据顺序。 | 时间排序测试覆盖同月、同季多个地点、结束边界及稳定排序。 |
| FR-13 | 路线节点必须保留机器时间、显示标签、地点类型和动作说明；派生返回节点必须标记为非真实事件。 | 路线数据测试检查 `date`、`dateLabel`、`kind` 与 `action`。 |
| FR-14 | 时间轴只能为真实的 `phase`、`stay`、`visit` 节点渲染刻度，不得为派生返回节点渲染刻度；三种节点保持不同视觉强度。 | `pnpm check:map` 检查主基地、次基地、普通旅行刻度及无派生回程按钮。 |
| FR-15 | 迁移完成后，当前已确认事实必须保留：成都为 2018 夏且从兰州往返；2020.7 高考后从兰州到庆阳并从庆阳进入南京；~~杭州期间的庆阳行程返回杭州~~（已由 FR-18 按用户更正为实习期间未回庆阳）。 | 生产数据回归测试断言成都和 2020 阶段承接；杭州事实由 FR-18 覆盖。 |
| FR-16 | 现有自动播放、手动步进、点击/拖动时间轴、Home/End/方向键定位行为不得改变。 | `pnpm check:map` 全部交互断言通过。 |
| FR-17 | 相邻且具有相同非空 `journeyId` 的 `visit` 必须组成显式连续行程；组内地点按机器时间和 `sequence` 依次连接，只在最后一个地点后返回当前基地。没有 `journeyId` 的访问继续遵循 FR-8。 | 合成测试验证 `基地 → A → B → C → 基地`，且普通访问仍为 `基地 → A → 基地`。 |
| FR-18 | 2023 年杭州实习期间不得包含庆阳行程；路线必须为 `杭州 → 嘉兴 → 杭州 → 南京（夏令营）→ 杭州 → 南京 → 青岛 → 淄博 → 泰安 → 北京 → 南京`。 | 生产数据回归测试断言杭州子事件、杭州结束承接和华北连续行程的完整相邻顺序。 |
| FR-19 | 2023 年与家人的嘉兴行程必须以“嘉兴”作为城市节点并点亮嘉兴市，不再把乌镇作为独立地图节点或使用乌镇坐标。 | 数据测试检查城市名、备注及无显式乌镇坐标；地图坐标注入必须从城市数据解析嘉兴市。 |
| FR-20 | 地图页面的产品名称必须统一为“人生足迹”，不得继续显示“旅行足迹”。 | 生产页面标题、顶栏标题和迁移脚本模板均通过文本验证。 |
| FR-21 | 地图必须支持键盘操作：地点条目使用 Enter/Space；时间轴使用左右方向键、Home、End；非交互元素聚焦时使用 J 启动或退出人生轨迹、Space 暂停或继续、左右方向键前后步进、Escape 退出。原生按钮和 Leaflet 地图键盘行为不得被全局快捷键拦截。 | 浏览器回归通过键盘启动、暂停、步进和退出，并继续覆盖时间轴 Home/End。 |
| FR-22 | 2024 年云南旅行必须显式组成 `南京 → 西双版纳 → 大理 → 丽江 → 昆明 → 南京` 的连续行程，只在昆明后返回南京；之后从南京前往杭州参加编译比赛并返回南京；后续无锡、镇江仍为普通访问。 | 生产数据回归断言云南四个地点共享 `journeyId`、中间没有南京，并在最终回程后紧接 `南京 → 杭州 → 南京`。 |
| FR-23 | Marker 强调和缩放动画不得写入 Leaflet Marker 外层的定位 `transform` 或为其添加 transform transition；缩放、平移后 Marker 必须保持有效坐标且不堆积、不延迟偏移。 | 浏览器回归悬停地点后检查外层 transform 仍由 Leaflet 管理，并在缩放后重新检查 Marker 分布。 |
| FR-24 | 已确认连续路线必须按以下顺序生成：2025 江南 `南京 → 苏州 → 上海 → 南京`；2025 深圳期间 `深圳 → 珠海 → 澳门 → 珠海 → 深圳`；2026 初 `北京 → 珠海 → 香港 → 珠海 → 北京`；2026 东北 `北京 → 哈尔滨 → 长春 → 沈阳 → 北京`；2026.6 `南京 → 庆阳 → 西安 → 珠海 → 深圳 → 惠州 → 广州 → 南昌 → 九江 → 南京 → 北京`。 | 生产数据回归逐段断言完整相邻顺序、重复珠海节点及每段仅在最终地点后派生一次回程；2026.6 庆阳为连续行程访问而非次基地。 |

## Success Criteria

1. 用户查看 2020 年路线时，地图稳定呈现 `兰州 → 庆阳 → 南京`，不再显示庆阳后返回兰州。
2. 用户查看任何次主基地期间的短程旅行时，路线都返回该次主基地而非外层主基地。
3. 两次普通旅行之间始终经过当时有效的主基地或次主基地。
4. 全部旅行节点按机器时间单调排列，同时保留月份、季节等原始显示精度。
5. 非法区间或基地归属在自动化验证中失败，不会静默进入地图。
6. 完整生产构建、内容验证和地图浏览器回归测试全部通过，现有地图交互和视觉不变。
7. 显式多城市行程只生成一次最终回程，且 2023 年杭州、嘉兴与华北路线符合用户确认的顺序。
8. 页面命名、键盘操作、云南及赛后杭州路线和缩放稳定性均通过浏览器与数据回归。
9. 2025 江南与深珠澳、2026 珠港、东北和六月长途路线均严格遵循用户确认的逐站顺序。

## Key Entities

- `PlaceNode`: 递归地点节点；包含 `kind`、城市、省份、日期、内容关联和可选子节点；位于 `src/data/travel.js`。
- `TravelDate`: 机器可读的 `start`、`end`、可选 `sequence`、`endSequence` 与显示 `label`；由 `src/lib/travel-time.js` 校验和比较。
- `BaseStack`: 路线派生过程中的当前主基地与嵌套次主基地栈；由 `src/lib/travel-journey.js` 内部维护。
- `JourneyStop`: 地图动画消费的扁平路线节点，区分真实事件和派生回程；由 `src/lib/travel-journey.js` 生成。
- `journeyId`: 可选的连续行程标识；只对相邻 `visit` 生效，不改变普通访问的默认回程语义。

## Assumptions

- 部分 ISO 日期继续使用 `YYYY`、`YYYY-MM` 或 `YYYY-MM-DD`，且同一需要比较的边界使用相同精度。
- 只知道季节时使用 `YYYY-spring/summer/autumn/winter`，分别以 3、6、9、12 月作为稳定排序锚点；该锚点不代表虚构的实际月份。
- `start = end` 只表示点状 `visit`，不表示空的持续驻留区间。
- `stay` 必须满足 `start < end`；`phase` 除当前阶段外也必须满足 `start < end`。
- 同一父容器中的两个 `stay` 不得重叠；`visit` 可以位于一个 `stay` 内，但必须作为该 `stay` 的子节点维护。
- 当开始或结束边界只能精确到同一月份时，使用 `sequence/endSequence` 表达已知先后，不补造具体日。
- 现有旅行事实除用户已经明确纠正的成都日期与 2020 年阶段切换外，不在本功能中重新解释。
- 地点坐标、文章关联、颜色和说明字段在模型迁移时原样保留。
- 连续行程必须由数据显式声明，系统不得仅凭相邻日期或地点自动合并。

## Clarifications

- 主基地是否表示实际全程居住？不是；它表示人生阶段容器，事件间隙默认所在地才是主基地。
- 普通旅行持续时间未知时如何处理？作为 `start = end` 的短暂访问，不伪造日级时间。
- 次主基地期间短程旅行回哪里？返回当前基地栈顶部，即次主基地。
- 阶段结束前已经离开主基地怎么办？最后一个持续 `stay` 与阶段同时结束时，从该地点直接进入下一主基地。
- 是否继续使用 `oneWay`？不使用；阶段承接由时间区间和地点类型推导。

## Out of Scope

- 推测用户未提供的具体日期、时刻或旅行时长。
- 根据地图距离推导交通工具、道路或真实移动耗时。
- 根据相邻日期或地点自动猜测并组合多城市旅程。
- 修改地图视觉设计、主题、头像、侧栏和时间轴控件。
- GitHub 仓库创建、代码推送、Cloudflare Pages 配置与生产部署。
